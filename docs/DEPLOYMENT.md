# استقرار محصولات غذایی رویا — فاز ۵

سورس اصلی یک برنامهٔ Next.js با PostgreSQL است. پیش‌نمایش Sites یک خروجی استاتیک خصوصی برای بررسی ظاهر است؛ سفارش، پرداخت، ورود و ذخیرهٔ پنل در آن اجرا نمی‌شوند. دادهٔ نمونه و عکس نمونه را با اطلاعات واقعی فروشگاه جایگزین کنید. تست‌های فعلی اتصال واقعی بانک یا PostgreSQL را تأیید نمی‌کنند.

## آماده‌سازی مشترک

Node.js نسخهٔ 24 و npm نصب کنید. از فایل `.env.example` یک `.env` محلی بسازید؛ آن را در گیت ثبت نکنید. در محیط واقعی این متغیرها را تنظیم کنید:

| متغیر | کاربرد |
| --- | --- |
| DATABASE_URL | اتصال PostgreSQL در زمان اجرا؛ اتصال pool برای Vercel |
| DIRECT_URL | اتصال مستقیم PostgreSQL برای migration |
| NEXT_PUBLIC_SITE_URL، NEXTAUTH_URL | مبدأ HTTPS یکسان، بدون مسیر؛ دامنهٔ واقعی فروشگاه |
| NEXTAUTH_SECRET | راز تصادفی حداقل ۳۲ کاراکتر؛ تغییر آن نشست‌ها را باطل می‌کند |
| CLOUDINARY_CLOUD_NAME، CLOUDINARY_API_KEY، CLOUDINARY_API_SECRET | حساب واقعی Cloudinary؛ کلید secret فقط روی سرور |
| ZARINPAL_MERCHANT_ID | شناسهٔ پذیرنده؛ نبود آن پرداخت آنلاین را غیرفعال می‌کند |
| ZARINPAL_SANDBOX | برای آزمون `true`، برای پذیرندهٔ واقعی `false` |
| ROYA_DEMO_CATALOG | در محیط واقعی `0` |
| ROYA_INDEXABLE | ابتدا `0`؛ بعد از تکمیل اطلاعات و آزمون عملی `1` |

برای PostgreSQL راه دور از TLS و اعتبارسنجی گواهیِ توصیه‌شدهٔ ارائه‌دهنده استفاده کنید. رمزها را در secret manager یا فایل محدود به مالک نگه دارید. `NEXT_PUBLIC_*` عمومی است؛ هیچ راز یا اطلاعات مشتری را در آن قرار ندهید. این متغیرها در build استفاده می‌شوند؛ پس از تغییر دامنه یا تنظیمات سئو دوباره build و deploy کنید.

```sh
npm ci
npm run deploy:check
npm run db:deploy
npm run db:seed
npm run admin:create
npm test
npm run typecheck
npm run build
```

Seed فقط دسته‌بندی‌ها و تنظیمات اولیه را ایجاد می‌کند؛ مدیر، کالای ساختگی، قیمت یا منطقهٔ ارسال نمی‌سازد. دستور ساخت مدیر نام، موبایل و رمز را تعاملی می‌پرسد و حساب موجود را بازنویسی نمی‌کند. مدیر باید محصولات، مناطق ارسال، ساعات کاری و اطلاعات تماس را تکمیل کند. ورود در `/admin/login/` است. احراز هویت با موبایل و رمز، محدودیت تلاش ورود و بررسی نقش مدیر در هر درخواست اجرا شده است؛ 2FA اختیاری پیاده‌سازی نشده و حسابی که پرچم 2FA آن روشن باشد اجازهٔ ورود ندارد.

## Vercel

مخزن GitHub را import و framework را Next.js انتخاب کنید. متغیرهای بالا را در محیط Production و Preview به‌صورت جداگانه وارد کنید؛ Preview باید `ROYA_INDEXABLE=0` و پایگاه دادهٔ جداگانه داشته باشد. `SITES_STATIC_PREVIEW` را تنظیم نکنید. Build command برابر `npm run build` باشد؛ Output Directory را برای تشخیص خودکار Next.js خالی بگذارید.

migration را یک بار از محیط مطمئن متصل به دیتابیس با `npm run db:deploy` اجرا کنید؛ آن را در buildهای موازی Vercel اجرا نکنید. قبل از migration نسخهٔ پشتیبان بگیرید. پس از deploy دامنهٔ HTTPS را وصل کنید و دامنهٔ یکسان را در هر دو URL قرار دهید؛ سپس rebuild کنید. بارگذاری رسانه مستقیماً با امضای سرور به Cloudinary می‌رود تا محدودیت حجم درخواست Vercel مانع ویدیو نشود. ویدیو حداکثر ۲۰MB است و نتیجهٔ تبدیل نیز در سرور بررسی می‌شود.

## VPS با systemd و Caddy

روی سرور Linux، Node.js 24 در `/usr/bin/node`، PostgreSQL 17 یا ارائه‌دهندهٔ مدیریت‌شده و Caddy نصب کنید. DNS دامنه را به سرور وصل کنید؛ پورت‌های 80 و 443 را باز و PostgreSQL را از اینترنت عمومی جدا کنید. نمونهٔ محلی `compose.yaml` برای توسعه است، نه پیکربندی تولید.

سورس مخزن را در `/opt/roya/current` قرار دهید. این مسیر در فایل سرویس استفاده می‌شود. یک کاربر بدون ورود `roya` و پوشهٔ تنظیمات ایجاد کنید:

```sh
sudo useradd --system --home /opt/roya --shell /usr/sbin/nologin roya
sudo install -d -m 750 -o root -g roya /etc/roya
sudo install -m 640 -o root -g roya .env /etc/roya/roya.env
```

فرمان‌های آماده‌سازی مشترک را در `/opt/roya/current` اجرا کنید. سپس فایل‌های استاتیک را کنار standalone کپی کنید:

```sh
cp -r public .next/standalone/public
mkdir -p .next/standalone/.next
cp -r .next/static .next/standalone/.next/static
sudo chown -R roya:roya /opt/roya/current/.next
sudo cp deploy/roya.service /etc/systemd/system/roya.service
sudo systemctl daemon-reload
sudo systemctl enable --now roya
```

فایل `deploy/Caddyfile` را در `/etc/caddy/Caddyfile` قرار دهید. متغیر `ROYA_DOMAIN` را برای سرویس Caddy با دامنهٔ خودتان تنظیم کنید:

```sh
sudo systemctl edit caddy
```

در ویرایشگر مقدار واقعی را وارد کنید:

```ini
[Service]
Environment=ROYA_DOMAIN=shop.your-domain.example
```

این دامنه نمونه است و باید جایگزین شود. سپس:

```sh
sudo systemctl daemon-reload
sudo systemctl reload-or-restart caddy
curl --fail http://127.0.0.1:3000/api/health/
sudo journalctl -u roya --since today
```

Endpoint سلامت فقط وضعیت کلی اتصال دیتابیس را اعلام می‌کند و اطلاعات اتصال را برنمی‌گرداند. آن را با فاصلهٔ حداقل ۳۰ ثانیه پایش کنید. لاگ reverse proxy باید query string مسیر callback پرداخت و اطلاعات فرم را حذف کند؛ لاگ Next.js نباید به‌صورت عمومی منتشر شود. سرویس فقط روی localhost گوش می‌دهد؛ HTTPS را Caddy خاتمه می‌دهد. برای انتشار نسخهٔ بعد build را در مسیر release جدا انجام دهید، migration سازگار را اجرا کنید، فایل‌ها را کپی و symlink `current` را اتمیک جابه‌جا کنید؛ سپس سرویس را restart کنید. برای rollback برنامه، سازگاری دیتابیس را بررسی کنید؛ migration مخرب را صرفاً با بازگشت کد معکوس نکنید.

## نگهداری و بازیابی

از PostgreSQL هر روز نسخهٔ پشتیبان رمزنگاری‌شده در فضای جداگانه نگه دارید. آدرس اتصال مستقیم را با `PGSERVICE=roya` و فایل‌های `.pg_service.conf` / `.pgpass` با دسترسی `600` تنظیم کنید تا رمز در آرگومان فرمان یا تاریخچه قرار نگیرد:

```sh
PGSERVICE=roya pg_dump --format=custom --file=roya-backup.dump
PGSERVICE=roya_restore pg_restore --exit-on-error --no-owner --dbname=roya_restore roya-backup.dump
```

`roya_restore` باید سرویس و دیتابیس **جدا و خالی** باشد. ابتدا بازگردانی آزمایشی، شمارش سفارش‌ها و ورود مدیر را بررسی کنید؛ فایل backup را عمومی یا داخل مخزن نگذارید. Cloudinary جدا از دیتابیس است؛ حذف فایل ابری را پس از بررسی ارجاع‌ها انجام دهید. آرشیو محصول فایل را خودکار از Cloudinary حذف نمی‌کند.

برای پاک‌سازی روزانهٔ bucketهای منقضی‌شده، با محیط دیتابیس تنظیم‌شده اجرا کنید:

```sh
npm run maintenance:rate-limits
```

این دستور فقط bucketهای بیش از ۲۴ ساعت منقضی‌شده را حذف می‌کند. سفارش معلق، ظرفیت رزروشده، رسید پرداخت یا سابقهٔ مشتری را حذف نمی‌کند. پرداخت با نتیجهٔ نامعلوم را در داشبورد زرین‌پال بررسی کنید؛ آن را خودکار منقضی یا دوباره ایجاد نکنید. لغو سفارش پرداخت‌شده نیاز به بازپرداخت واقعی از طرف مدیر دارد؛ پنل وضعیت «نیازمند بازپرداخت» را نمایش می‌دهد و انتقال وجه انجام نمی‌دهد.

## پذیرش قبل از فروش واقعی

روی دیتابیس آزمایشی migration و ساخت مدیر را انجام دهید؛ سپس ورود صحیح/غلط، منع درخواست غیرمدیر، فرم Cloudinary، حد حجم ویدیو، مقدار حداقل/گام سفارش، قیمت دستکاری‌شده، ظرفیت هم‌زمان، تخفیف و ارسال شهری را آزمایش کنید. یک سفارش نقدی را تا تحویل و یک سفارش sandbox را تا callback موفق، تکرار callback و لغو/بازپرداخت بررسی کنید. پیگیری باید فقط با کد و موبایل صحیح پاسخ دهد. هزینهٔ ارسال و زمان تحویل برابر بیشترین زمان آماده‌سازی اقلام + زمان منطقه باشد. موبایل واقعی، جزئیات تماس، قیمت‌ها و هزینه‌ها را خودتان وارد کنید.

بعد از تأیید عملی، مرچنت واقعی، sandbox خاموش و `ROYA_INDEXABLE=1` را تنظیم و rebuild کنید. `/robots.txt` و `/sitemap.xml` را بررسی و sitemap را در Search Console ثبت کنید. صفحات سبد، پرداخت، پیگیری و ادمین noindex هستند. Product JSON-LD فقط برای کاتالوگ واقعی فعال می‌شود؛ UI قیمت تومان دارد و schema ارز رسمی IRR و مبلغ ×۱۰ را اعلام می‌کند. schema شامل واحد پایه و حداقل مقدار است؛ واجد شرایط بودن نمایش قیمت واحد در Google باید با Rich Results Test بررسی شود.

CSP مانع frame و object می‌شود و eval در production ندارد؛ برای سازگاری با hydration و ISR، script/style inline مجاز است و این سیاست nonce-based نیست. فرم‌های تغییردهندهٔ داده Origin، بدنهٔ محدود و Zod دارند؛ NextAuth از CSRF token استفاده می‌کند. نرخ درخواست‌ها در PostgreSQL مشترک است. هنگام استفاده از proxy فقط headerهای معتبر را از proxy خودتان عبور دهید؛ محدودیت کلی مستقل از IP نیز فعال است. تغییرات محیط/راز و بازیابی backup را ابتدا در محیط آزمایشی انجام دهید.

مراجع: [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying)، [Next.js metadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata)، [Product structured data](https://developers.google.com/search/docs/appearance/structured-data/product-snippet).

## ثبت‌نام و حساب مشتری

مسیر اصلی کد پروژه `E:\miranco.project\RoyaHomeMadeFood` است؛ پوشهٔ `Royahealthyfood` مخزن خالی است.

migration جدید `20261030090000_customer_registration_addresses` را با `npm run db:deploy` روی دیتابیس محیط مقصد اجرا کنید. سپس `CUSTOMER_ACCOUNTS_ENABLED=1`، `CUSTOMER_OTP_SECRET` تصادفی با حداقل ۳۲ نویسه، `KAVENEGAR_API_KEY` و `KAVENEGAR_OTP_TEMPLATE` را تنظیم کنید. تنظیم سرویس ایمیل فعلاً اختیاری است. [Lookup کاوه‌نگار](https://kavenegar.com/rest.html) و [ارسال ایمیل Resend](https://resend.com/docs/api-reference/emails/send-email). کلیدها و کدها در build یا لاگ چاپ نمی‌شوند؛ مسیر API کاوه‌نگار را در APM هم redact کنید.

ثبت‌نام نام، موبایل ایرانی، ایمیل و رمز ۱۲ تا ۱۲۸ نویسه‌ای می‌گیرد. فعلاً فقط کد موبایل تأیید می‌شود. حساب و نشست با مصرف اتمیک همان کد موبایل ساخته می‌شوند و ایمیل با `emailVerifiedAt=null` ذخیره می‌شود. تأیید ایمیل برای آینده به تعویق افتاده است. رمز با scrypt و salt تصادفی و کدها با HMAC وابسته به مرحله و مقصد نگهداری می‌شوند. هر کد ۵ دقیقه اعتبار و سقف ۵ تلاش دارد؛ کل فرایند حداکثر ۱۵ دقیقه است. ارسال مجدد حداقل ۶۰ ثانیه فاصله دارد و تلاش‌های ایمیل را صفر نمی‌کند. کد ارسال ناموفق فعال نمی‌شود. هیچ کد ثابت یا کد آزمایشی قابل ورود وجود ندارد.

ورود بعدی از provider مستقل `customer-password` با ایمیل یا موبایل و رمز ثابت انجام می‌شود و به دسترس‌پذیری سرویس پیامک یا ایمیل وابسته نیست. provider `customer-registration` فقط کد موبایل ثبت‌نام را مصرف می‌کند؛ ورود پیامکی قدیمی حذف شده است. مدیر، حساب غیرفعال و حساب بدون تأیید موبایل اجازه ورود مشتری ندارند. اعضای قدیمی بدون رمز می‌توانند با اثبات موبایل ثبت‌نام را تکمیل کنند؛ شناسه، سفارش‌ها و رضایت قبلی آن‌ها حفظ و نشست‌های قدیمی ابطال می‌شود. ثبت‌نام دوباره حساب دارای رمز را بازنویسی نمی‌کند. بازیابی رمز مشتری هنوز در این تغییر پیاده‌سازی نشده است.

checkout واقعی داخلی و بین‌المللی نشست مشتری می‌خواهد. کاربر در همان صفحه وارد می‌شود یا ثبت‌نام را تکمیل می‌کند و به همان مسیر با سبد قبلی برمی‌گردد؛ هنگام پرداخت کد موبایل مجدد گرفته نمی‌شود. سفارش به خریدار واردشده وصل می‌شود، حتی اگر نام و موبایل گیرنده متفاوت باشد. کلید idempotency به حساب خریدار نیز وابسته است. سوابق مهمان قدیمی خودکار با تطبیق شماره به حساب منتقل نمی‌شوند؛ پیگیری قدیمی با کد و موبایل باقی است.

پنل حساب ۲۰ سفارش آخر با وضعیت سفارش و پرداخت و حداکثر ۲۰ آدرس عنوان‌دار را نمایش می‌دهد. هر آدرس نام و موبایل گیرنده، محدوده ارسال، نشانی و مختصات اختیاری دارد. ایجاد، ویرایش و حذف آدرس در سرور به مالک محدود است. انتخاب آدرس در checkout مشخصات گیرنده و موقعیت نقشه را پر و قیمت قبلی را باطل می‌کند تا هزینه ارسال دوباره بررسی شود. رضایت تبلیغات همچنان اختیاری و قابل لغو است؛ خبرها و پیشنهادهای باشگاه حفظ شده‌اند.

پیش‌نمایش استاتیک قابلیت ثبت‌نام واقعی ندارد؛ آزمایش پرداخت نمونه مستقل باقی می‌ماند. پیش از راه‌اندازی، migration، رقابت مصرف کد/ارسال مجدد و سفارش را روی PostgreSQL آزمایشی بررسی و ارسال واقعی پیامک و ایمیل و ورود/خروج را با شماره و ایمیل متعلق به خود آزمایش کنید. تست‌های mock تأیید ارسال واقعی نیستند. چالش‌های مصرف‌شده/منقضی را با سیاست نگهداری کوتاه پاک کنید و سابقه رضایت را نگه دارید.

## صندوق تماس، خبرهای باشگاه و امنیت مدیر

migration `20261011130000_club_announcements` را اجرا کنید. `/admin/communications/` صندوق فرم تماس با فیلتر و صفحه‌بندی و علامت خوانده‌شده/نشده دارد. خبر باشگاه با متن فارسی/انگلیسی و بازهٔ شمسی قابل ساخت و ویرایش است. خبر فقط در حساب واردشدهٔ مشتری و در بازهٔ فعال نمایش داده می‌شود؛ متن HTML اجرا نمی‌شود. ویرایش دارای نسخهٔ `updatedAt` است و تغییر هم‌زمان را رد می‌کند. صندوق تماس ایمیل یا پیامک ارسال نمی‌کند؛ علامت خوانده‌شده به معنی پاسخ‌دادن نیست.

در تنظیمات پنل مدیر امکان تغییر رمز با بررسی رمز فعلی و ابطال نشست‌های قبلی وجود دارد. برای بازیابی رمز فراموش‌شده، مالک سرور با دسترسی دیتابیس از ترمینال تعاملی معتبر `npm run admin:recover` را اجرا کند. دستور موبایل مدیر موجود، تأیید RESET و دو بار رمز جدیدِ مخفی را می‌پرسد؛ نقش را تغییر نمی‌دهد، حساب غیرفعال را فعال نمی‌کند و 2FA را دور نمی‌زند. این مسیر endpoint عمومی ندارد و عمل بازیابی audit می‌شود.

## آزمون‌های PostgreSQL واقعی

Workflow `.github/workflows/quality.yml` با PostgreSQL 17 جداگانه، migration، دوبار seed، TypeScript، تست‌های معمولی، آزمون‌های دیتابیس و build سروری/نمایشی را اجرا می‌کند. اجرای آن در محیط GitHub به فعال بودن Actions مخزن نیاز دارد. وجود workflow به تنهایی مدرک قبولی CI نیست؛ نتیجهٔ اجرای هر commit را در Actions بررسی کنید.

برای اجرای دستی آزمون دیتابیس، فقط روی یک دیتابیس **جداگانه و قابل حذف** با نام `roya_test` یا `roya_integration_test`، هر سه متغیر `DATABASE_URL`، `DIRECT_URL` و `ROYA_INTEGRATION_DATABASE_URL` را به همان دیتابیس تنظیم کنید. سپس:

```sh
npm ci
npm run db:deploy
npm run db:seed
npm run test:integration
```

این آزمون‌ها سفارش‌های ساختگی با نام مشخص ایجاد و فقط fixtureهای خودشان را پاک می‌کنند؛ fallback به دیتابیس فروشگاه ندارند. موجودی/ظرفیت آخر تحت سفارش هم‌زمان، idempotency سفارش، مصرف هم‌زمان OTP، اتصال سفارش به حساب، لغو و آزادسازی یک‌باره، تغییر رمز و نسخهٔ خبر روی PostgreSQL واقعی آزموده می‌شوند. هیچ پیامک یا پرداخت واقعی در این suite ارسال نمی‌شود. آزمون‌های محلی unit/mock و build را مستقل از نتیجهٔ CI گزارش کنید. اجرای عمومی فروشگاه همچنان نیازمند دادهٔ واقعی، دامنه، secretها و آزمون سرویس‌های بیرونی است.

## وابستگی‌ها و نصب تازه

`db:seed` پیش از اجرا Prisma Client را تولید می‌کند و seed در تابع async اجرا می‌شود تا نصب تازه با tsx/CJS هم کار کند. Seed دوباره‌اجراشدنی است و اطلاعات کسب‌وکار موجود را بازنویسی نمی‌کند. در `package.json`، override محدود `@prisma/config → deepmerge-ts@8.0.2` و `mysql2@3.24.5` برای اصلاح advisoryهای وابستگی‌های جانبی Prisma ثبت شده است؛ نسخهٔ اصلی Prisma 7.10.0 تغییر نکرده. پیکربندی فعلی object/array ساده دارد و از تفاوت ادغام Map در deepmerge 8 استفاده نمی‌کند. هر تغییر آیندهٔ این overrideها باید با generate، migrate، seed دوباره، integration و build بررسی شود. [انتشار deepmerge 8](https://github.com/RebeccaStevens/deepmerge-ts/releases/tag/v8.0.0) و [انتشار mysql2](https://github.com/sidorares/node-mysql2/releases). CI بررسی `npm audit --audit-level=high` را نیز اجرا می‌کند؛ قبولی امروز جایگزین پایش وابستگی‌ها در آینده نیست.

## مدیران و سطح دسترسی

migration `20261030100000_admin_permissions` مدیران فعلی را به مدیر اصلی تبدیل می‌کند؛ حساب‌های جدید پیش‌فرض هیچ دسترسی مدیریتی ندارند. مدیر اصلی در `/admin/users/` با موبایل یا ایمیل و رمز موقت ۱۲ تا ۱۲۸ نویسه‌ای ادمین می‌سازد یا مشتری موجود را ارتقا می‌دهد. هویت و سوابق مشتری حفظ و نشست‌های قبلی باطل می‌شوند. رمز مشترک یا ازپیش‌نوشته‌شده در کد وجود ندارد.

ورود ادمین با موبایل یا ایمیل انجام می‌شود. مدیر جدید یا مدیری که رمز او بازنشانی شده، پیش از استفاده از پنل باید در `/admin/security/` رمز شخصی تعیین کند. مدیر اصلی می‌تواند دسترسی‌ها، فعال‌بودن و رمز موقت سایر ادمین‌ها را تغییر دهد؛ تغییر مجوز یا رمز نشست‌های آن مدیر را باطل می‌کند. خود مدیر اصلی از این صفحه قابل غیرفعال‌سازی یا تنزل نیست. ساخت مدیران دیگر فقط به مدیر اصلی اختصاص دارد.

مجوزها: محصولات/رسانه، سفارش/ارسال، تأیید پرداخت، تغییر حساب‌های بانکی، محدوده/کرایه، تخفیف، پیام‌ها، مشتریان، و تنظیمات تماس/سئو/پیامک. فرم‌ها و منوها بر اساس مجوز نمایش داده می‌شوند و APIها مستقل از رابط مجوز را از دیتابیس بررسی می‌کنند. اطلاعات بانکی تنظیمات به ادمین فاقد مجوز بانکی برگردانده نمی‌شود. دسترسی سفارش اجازه تغییر شماره کارت نمی‌دهد؛ دسترسی تأیید پرداخت نیز جداست. عملیات ساخت/ارتقا/تغییر مجوز/بازنشانی رمز در AdminAudit ثبت می‌شود و رمزها در پاسخ API قرار نمی‌گیرند.

استقرار پنل به تنظیم Resend وابسته نیست؛ ثبت‌نام جدید فعلاً به تنظیم یا تأیید ایمیل وابسته نیست. توقف موجود پیامک و بودجه پنج تلاش تست حفظ شده و هیچ ارسال واقعی خودکار از build، تست واحد یا CI صورت نمی‌گیرد. برای تست عملی یک پیامک و یک ایمیل به مقصد تأییدشده مالک کافی است؛ تکرار خودکار ارسال انجام ندهید.

## راه‌اندازی ایمیل از پنل مدیر اصلی

در `/admin/settings/` بخش «ایمیل و آمادگی ثبت‌نام مشتری» فقط برای مدیر اصلی نمایش داده می‌شود. ساخت حساب Resend و تأیید دامنه/زیردامنه متعلق به فروشگاه باید ابتدا در خود سرویس انجام شود؛ هیچ حساب یا اشتراک خارجی خودکار ساخته نمی‌شود. برای نمونه می‌توان زیردامنه `mail.royahealthyfood.ir` و فرستنده `account@mail.royahealthyfood.ir` را پس از تأیید آن زیردامنه استفاده کرد. رکوردهای دقیق DNS را فقط از داشبورد Resend کپی کنید، نه از نمونه‌های ثابت. [راهنمای رسمی دامنه](https://resend.com/docs/dashboard/domains/introduction).

کلید با دسترسی ارسال را داخل فرم امن پنل وارد کنید. ذخیره تنظیمات ایمیلی نمی‌فرستد. کلید با AES-256-GCM، nonce تصادفی و کلید مشتق‌شده از NEXTAUTH_SECRET در Setting با کلید `customer-email` نگهداری می‌شود و هیچ APIای مقدار آن را برنمی‌گرداند. نسخه پشتیبان دیتابیس و NEXTAUTH_SECRET را خصوصی نگه دارید؛ تغییر این راز نیازمند ورود دوباره کلید ایمیل در پنل است. فقط مدیر اصلی اجازه ذخیره تنظیمات و تست دارد؛ مجوز عمومی «تنظیمات» کافی نیست.

پس از ذخیره، ایمیل خود مدیر را در فرم تست وارد کنید و دکمه ارسال را بزنید. این یک ارسال واقعی، با سقف ۳ تلاش برای هر مدیر در ساعت و ۱۰ تلاش کلی است. پذیرش درخواست توسط سرویس به معنی رسیدن به inbox نیست؛ مدیر باید کد ۶ رقمی دریافتی را در پنل وارد کند. کد ۵ دقیقه معتبر و حداکثر ۵ تلاش دارد و به مرحله تست اختصاص دارد؛ برای ورود مشتری قابل استفاده نیست. تغییر فرستنده یا کلید، تأیید تست را باطل می‌کند. فقط پس از تأیید دریافت، سرویس ایمیل آماده محسوب می‌شود؛ این سرویس فعلاً شرط ثبت‌نام نیست. فعال‌شدن ثبت‌نام به روشن‌بودن حساب مشتری، تنظیم پیامک و لغو توقف پیامک نیز وابسته است؛ پنل وضعیت این موارد را نشان می‌دهد. بودجه آزمایشی پیامک تغییری نمی‌کند و هیچ تست ایمیلی پیامک نمی‌فرستد.

متغیرهای محیطی RESEND_API_KEY و CUSTOMER_EMAIL_FROM همچنان برای نصب‌های قبلی پشتیبانی می‌شوند؛ وجود تنظیمات پنل بر آن‌ها اولویت دارد. در پنل، کلید خالی یعنی حفظ کلید قبلی و هیچ placeholder به‌عنوان کلید ذخیره نمی‌شود. عملیات تنظیم، ارسال تست و تأیید تست در AdminAudit بدون کلید یا کد ثبت می‌شوند.

## تکمیل تجربه حساب مشتری

ثبت‌نام نیمه‌کاره با نگهداری فقط شناسه تصادفی چالش در sessionStorage همان زبانه قابل بازیابی است؛ رمز، هش رمز، کد و verifier در مرورگر ذخیره نمی‌شوند. پس از رفرش، وضعیت معتبر از سرور خوانده می‌شود و مرحله موبایل یا ایمیل ادامه می‌یابد. ارسال مجدد خودکار وجود ندارد؛ پس از بازیابی مرحله موبایل، برای درخواست پیامک جدید باید ثبت‌نام را با ورود دوباره رمز شروع کرد. مرحله ایمیل به تأیید دوباره موبایل نیاز ندارد. پایان موفق یا شروع مجدد، شناسه ذخیره‌شده را پاک می‌کند.

تاریخچه خرید اکنون صفحه‌بندی شده است (۲۰ سفارش در هر صفحه) و به ۲۰ سفارش آخر محدود نیست. پیگیری از حساب ابتدا مالکیت userId را بررسی می‌کند و سپس اطلاعات لازم برای مسیر پیگیری موجود را می‌گیرد؛ شماره گیرنده در URL قرار نمی‌گیرد و سفارش حساب دیگری با کد آن قابل دریافت نیست. مشتری می‌تواند با رمز فعلی، رمز خود را تغییر دهد؛ sessionVersion افزایش می‌یابد و ورود دوباره با رمز جدید لازم است. تأیید موبایل و ایمیل حفظ می‌شود. بازیابی رمز فراموش‌شده هنوز جزو این مرحله نیست.


### تعویق موقت تأیید ایمیل

ثبت‌نام با نام، موبایل، ایمیل و رمز شروع و با کد معتبر موبایل تمام می‌شود. هیچ ایمیل خودکاری در این مسیر ارسال نمی‌شود. ایمیل تأییدنشده می‌ماند؛ ورود با ایمیل یا موبایل و رمز، آدرس‌ها، تغییر رمز و اتصال سفارش به حساب به تأیید موبایل وابسته‌اند. پنل تنظیمات ایمیل برای راه‌اندازی آینده حفظ شده است. توقف و بودجه تست پیامک تغییر نمی‌کنند.
