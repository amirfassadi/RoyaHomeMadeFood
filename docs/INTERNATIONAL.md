# خرید از خارج، تحویل در ایران

صفحات `/fa/international/` و `/en/international/` به سبد مشترک فروشگاه وصل‌اند. خریدار ایمیل خودش و نام، موبایل ایرانی، نشانی و محدودهٔ گیرنده را وارد می‌کند. خرید مهمان است؛ موبایل گیرنده حساب خریدار محسوب نمی‌شود و سفارش به حساب هم‌نام متصل نمی‌شود. ایمیل فقط برای پشتیبانی ذخیره می‌شود؛ ارسال ایمیل خودکار پیاده‌سازی نشده است. ارسال خارج کشور وجود ندارد.

## دامنه و کشور بازدیدکننده

بنر خرید خارج پس از پاسخ API بدون cache و فقط برای کشور غیر ایران نمایش داده می‌شود. زبان سایت و موبایل تعیین‌کنندهٔ کشور نیستند. در اتصال ناشناخته، ایران، Tor یا کشور نامعتبر، پرداخت ارزی غیرفعال است. صفحات توضیحی قابل بازشدن با لینک مستقیم‌اند؛ محدودیت کشور روی API ثبت سفارش و استعلام ارزی نیز اعمال می‌شود. سایت اصلی و کاتالوگ همچنان در دسترس‌اند.

`ROYA_TRUST_GEO_HEADER=1` فقط پس از راه‌اندازی proxy معتبر مجاز است. proxy باید `X-Roya-Country` ورودی کاربر را حذف و خودش از پایگاه GeoIP معتبر مقدار دهد. اگر از Cloudflare استفاده می‌شود، origin را با firewall به IPهای رسمی Cloudflare محدود کنید، IPv4 و IPv6 و مسیرهای جانبی را پوشش دهید و سپس Nginx مقدار `CF-IPCountry` تأییدشده را به `X-Roya-Country` نگاشت کند. صرف داشتن header از اینترنت، مدرک کشور نیست. برنامه روی localhost گوش می‌دهد و دسترسی مستقیم به پورت آن نباید باز شود. API کشور باید از cache پراکسی/CDN مستثنا باشد. پیاده‌سازی GeoIP به تنظیم نهایی DNS/VPS وابسته است؛ این تغییر خودش روی VPS چیزی نصب نمی‌کند. تشخیص IP تقریبی است و جایگزین احراز هویت یا بررسی شرایط پذیرندگی نیست.

پیش‌نمایش استاتیک Sites API ندارد: بنر کشور فعال نیست و پرداخت نمایشی/واقعی انجام نمی‌شود. برای بررسی ظاهر از لینک مستقیم صفحه استفاده کنید. مرورگر ایران یا بدون کشور معتبر نباید بتواند با POST مستقیم به API ارزی سفارش بسازد. در محیط آزمایش با proxy کنترل‌شده، کشور ایران، خارج، نامشخص و header جعلی را بررسی کنید.

## BTCPay Greenfield

اتصال اولیه برای BTCPay Server نوشته شده است؛ ایجاد حساب تجاری یا نصب نود در این تغییر انجام نشده است. پذیرش اولیه برای Bitcoin و در صورت فعال‌بودن در فروشگاه BTCPay، Lightning است؛ USDT یا همهٔ شبکه‌ها وعده داده نمی‌شود. برای استفاده از سرویس میزبان ثالث، مجازبودن فعالیت فروشگاه ایرانی را جداگانه بررسی کنید. نمایش بخش به IP خارجی محدودیت‌های پذیرندگی را تغییر نمی‌دهد.

BTCPay/نود را روی VPS فعلی ۱GB با ۵GB فضای آزاد نصب نکنید. یک نمونهٔ مستقل، آزمایشی و سپس عملیاتی لازم است. آدرس، شناسهٔ فروشگاه، API key محدود به همان فروشگاه با `btcpay.store.cancreateinvoice` و `btcpay.store.canviewinvoices`، و webhook secret را فقط در محیط سرور بگذارید. هیچ seed phrase یا private key کیف پول در این برنامه لازم نیست.

متغیرها در `.env.example` هستند:

- `ROYA_INTERNATIONAL_ENABLED=1` پس از آزمون و تنظیم proxy.
- `BTCPAY_URL`: مبدأ HTTPS بدون مسیر، query یا credential.
- `BTCPAY_STORE_ID` و `BTCPAY_API_KEY`.
- `BTCPAY_WEBHOOK_SECRET`: راز تصادفی حداقل ۳۲ کاراکتر که همان مقدار در webhook فروشگاه BTCPay تنظیم شده باشد.
- `ROYA_USD_RATE_TOMAN`: عدد صحیح تومان برای یک دلار که مالک فروشگاه تعیین می‌کند؛ نرخ زندهٔ بازار نیست.
- `ROYA_USD_RATE_EXPIRES_AT`: پایان اعتبار صریح با زمان UTC، مثلاً قالب `YYYY-MM-DDTHH:mm:ssZ`. پس از انقضا سفارش ارزی جدید متوقف می‌شود. متغیرها بعد از تغییر نیازمند restart سرویس هستند؛ راز را در گیت نگذارید.

Webhook فروشگاه را به `https://YOUR_SHOP/api/payment/crypto/webhook/` وصل کنید، رویدادهای invoice را فعال و redelivery را تنظیم کنید. فاکتور ۱۵ دقیقه اعتبار، tolerance صفر و سیاست MediumSpeed دارد. مطمئن شوید فروشگاه برای Bitcoin تعداد تأییدیهٔ مناسب دارد و روش موردنظر فعال است. شبکه/مبلغ کریپتو را خود درگاه در فاکتور نشان می‌دهد؛ مشتری باید دقیقاً همان شبکه را استفاده کند.

## مبلغ و تأیید

محاسبهٔ موجودی، حداقل/گام، تخفیف و ارسال همان مسیر تراکنشی سفارش داخلی است. مبلغ تومان مرجع داخلی است؛ کل سفارش یک بار با محاسبهٔ صحیح و گردکردن رو به بالا به سنت دلار تبدیل می‌شود. مبلغ دلار، نرخ و پایان اعتبار آن همراه سفارش snapshot می‌شوند. مبلغ ارسالی مرورگر فقط برای تشخیص تغییر قیمت استفاده می‌شود. در فاکتور خارجی فقط مبلغ USD و شناسه‌های سفارش ارسال می‌شوند؛ نشانی، موبایل و ایمیل گیرنده ارسال نمی‌شوند.

ساخت فاکتور یک بار claim می‌شود. timeout یا پاسخ نامطمئن حالت UNKNOWN می‌دهد؛ درخواست خودکار دوم وجود ندارد. نتیجهٔ برگشت مرورگر، رسید ارسالی یا ادعای txid هیچ‌کدام سفارش را PAID نمی‌کنند. webhook باید HMAC-SHA256 روی بایت‌های خام و مقایسهٔ constant-time داشته باشد. سپس برنامه فاکتور را مجدداً از API دارای اعتبارنامه می‌خواند، store/origin، شناسه فاکتور، metadata سفارش/تلاش، ارز و مبلغ را تطبیق می‌دهد. URL درگاه فقط در همان origin مجاز است. فقط `Settled` با `additionalStatus=None` پرداخت قطعی خودکار می‌شود. Processing، کمتر/بیشتر از مبلغ، پرداخت دیرهنگام، Expired و Invalid نیازمند بررسی‌اند. تکرار webhook/استعلام بی‌اثر است؛ زمان آماده‌سازی بعد از تأیید از نو محاسبه می‌شود.

پنل جزئیات سفارش مبلغ USD، ایمیل خریدار و وضعیت فاکتور را نشان می‌دهد. «بررسی پرداخت با درگاه» دوباره API را می‌خواند. اگر ساخت فاکتور نامطمئن مانده، اپراتور شناسه را از BTCPay پیدا و وارد می‌کند؛ برنامه قبل از اتصال metadata و مبلغ را تأیید می‌کند. اگر درگاه فاکتور را نساخته باشد، اپراتور باید مورد را بررسی کند؛ reset خودکار UNKNOWN به NEW نداریم. با تغییر origin/store باید سفارش‌های قبلی را قبل از حذف اتصال قدیمی تطبیق داد.

برای سفارش کریپتوِ پرداخت‌نشده، رفتن به آماده‌سازی ممنوع است. لغو پیش از آغاز درخواست یا پس از پرداخت ممکن است؛ لغو پرداخت‌شده علامت بازپرداخت دستی دارد. رزروِ درخواست نامطمئن، منقضی یا دارای پرداخت جزئی خودکار آزاد نمی‌شود و endpoint برای دورزدن این محافظ وجود ندارد. این موارد به تطبیق اپراتوری و در صورت نیاز فرایند جبرانی کنترل‌شده نیاز دارند. برنامه بازپرداخت کریپتو را انجام نمی‌دهد. اگر تسویهٔ معتبر پس از لغو شناسایی شود، سفارش لغوشده باقی می‌ماند و نیازمند بازپرداخت می‌شود. مبلغ بیشتر/جزئی/دیررس را در BTCPay و پشتیبانی پیگیری کنید؛ آن‌ها خودکار به سفارش عادیِ پرداخت‌شده تبدیل نمی‌شوند.

## راه‌اندازی و آزمون

migration را با `npm run db:deploy` اجرا کنید؛ `deploy:check` تنظیمات فعال‌سازی را بررسی می‌کند. ابتدا BTCPay آزمایشی با Bitcoin testnet/regtest و کیف پول آزمایشی، بدون پول واقعی راه بیندازید. موفقیت و تکرار webhook، امضای غلط، مبلغ اشتباه، فاکتور نامرتبط، وقفهٔ شبکه هنگام ساخت، پرداخت جزئی/دیر/اضافی، انقضای نرخ، رقابت سفارش/لغو و بازیابی invoice را بررسی کنید. کلید API، مسیرهای حساس و داده‌های webhook را در لاگ عمومی چاپ نکنید.

تست‌های خودکار، API درگاه را mock می‌کنند؛ integration PostgreSQL snapshot، idempotency، موجودی و گارد آماده‌سازی/لغو را با دیتابیس واقعی می‌سنجد. این تست‌ها مدرک پرداخت واقعی، تنظیم موفق GeoIP یا نصب BTCPay نیستند. پیش از فعال‌کردن دریافت وجه، آزمون کامل محیط واقعی الزامی است.
