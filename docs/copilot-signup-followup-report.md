# گزارش پیگیری مرحله دوم ثبت‌نام بدون OTP

## علت و اصلاح نقص
ثبت‌نام و ورود با رمز قبلاً بدون OTP انجام می‌شد، اما برخی مسیرها و رابط کاربری همچنان تأیید موبایل را شرط می‌گرفتند. یک نقص مالکیتی جداگانه نیز وجود داشت: پاسخ پیام تماس مهمان با جست‌وجوی موبایل به حساب مشتری وصل می‌شد، حتی اگر آن شماره تأیید نشده بود.

حساب دارای نشست معتبر، نقش `CUSTOMER`، وضعیت فعال و `sessionVersion` جاری اکنون بدون تأیید تماس می‌تواند از حساب، خرید، آدرس، تغییر رمز و چت پشتیبانی خودش استفاده کند. در صفحه حساب، تغییر رمز و مدیریت آدرس دیگر به `mobileVerified` وابسته نیستند؛ پشتیبانی نیز بر مبنای نشست مشتری در دسترس است. وضعیت تأیید موبایل و ایمیل همچنان جداگانه و صادقانه نمایش داده می‌شود. متن checkout اکنون می‌گوید سفارش به حساب واردشده وصل می‌شود و موبایل گیرنده برای هماهنگی تحویل است.

پاسخ به پیام قدیمی/مهمان فقط در صورت وجود مشتری فعال با همان موبایلِ تأییدشده به حساب متصل می‌شود. موبایل تأییدنشده مجوز ساخت `userId` یا `customerNotice` نیست. چت پشتیبانی حساب خودش مستقل از پیام مهمان است و با `userId` نشست کار می‌کند.

## مالکیت داده‌ها
- نشست با شناسه حساب از دیتابیس بازبینی می‌شود؛ نقش، فعال‌بودن و `sessionVersion` در helper مشترک کنترل می‌شوند.
- سفارش‌ها، تاریخچه، تیکت پشتیبانی و گزارش پرداخت با `userId` محدود می‌شوند؛ موبایل گیرنده یا ایمیل مبنای بازیابی داده‌های قدیمی نیست.
- ایجاد/ویرایش/حذف آدرس با `userId` مقید است؛ تلاش کاربر دیگر برای تغییر یا حذف آدرس رد می‌شود.
- سفارش جدید با `customerId` نشست معتبر به همان حساب وصل می‌شود. برای حساب ایمیل‌محور، checkout همچنان شماره موبایل گیرنده را می‌گیرد و schema آن را اعتبارسنجی می‌کند؛ این شماره هویت خریدار یا دلیل اتصال سفارش نیست.
- تغییر رمز رمز فعلی را بررسی می‌کند، در تراکنش `sessionVersion` را افزایش می‌دهد و وضعیت تأیید تماس را تغییر نمی‌دهد.
- اتصال پاسخ پیام تماس مهمان، برخلاف چت حساب، همچنان نیازمند اثبات مالکیت قبلیِ شمارهٔ تأییدشده است.

## فایل‌های این اصلاح
- `src/lib/server/contact-replies.ts` — بازگرداندن شرط مشتری فعال و موبایل تأییدشده برای اتصال پیام مهمان به حساب.
- `src/lib/server/support.ts` و `src/app/[locale]/support/page.tsx` — حذف شرط تأیید از چت حساب خود مشتری.
- `src/components/store/customer-account.tsx` — فعال‌کردن مدیریت آدرس و تغییر رمز برای حساب واردشده، با حفظ برچسب‌های وضعیت تماس.
- `src/components/store/checkout-form.tsx` — اصلاح توضیح اتصال سفارش و موبایل گیرنده.
- `tsconfig.json` — افزودن `RoyaHomeMadeFood` به `exclude` پروژه اصلی؛ محتوای پوشه مستقل تغییر نکرد.
- `tests/server/contact-replies.test.ts` — جلوگیری از اتصال پاسخ مهمان به حساب دارای موبایل تأییدنشده.
- `tests/server/support.test.ts` — دسترسی چت برای حساب ایمیل‌محور و موبایل‌محور بدون تأیید.
- `tests/server/customer-account.test.ts` و `tests/server/customer.test.ts` — تغییر رمز، آدرس و جلوگیری از دسترسی کاربر دیگر برای حساب‌های بدون تأیید.
- `tests/server/shipping-checkout.test.ts` — اتصال خرید حساب‌های موبایل‌محور و ایمیل‌محور به `userId`، با رد نشست منقضی.
- `tests/integration/postgres.test.ts` — افزودن سناریوی PostgreSQL ثبت‌نام جدید بدون OTP برای هر دو نوع حساب، آدرس و مالکیت، تغییر رمز و اتصال سفارش؛ پاک‌سازی fixture آدرس با حذف آبشاری کاربر انجام می‌شود.

## تصحیح گزارش قبلی
گزارش قبلی به‌اشتباه نوشته بود محدودیت‌های رابط کاربری قبلاً هماهنگ شده و typecheck/build پروژه اصلی موفق بوده‌اند. بررسی مجدد نشان داد UI هنوز تغییر رمز، آدرس و پشتیبانی را به تأیید موبایل وابسته می‌کرد و `tsconfig.json` فایل‌های `RoyaHomeMadeFood` را وارد بررسی رسمی می‌کرد؛ فرمان‌های رسمی در آن وضعیت خطاهای TypeScript همان پروژه مستقل را گزارش می‌دادند. این محدودیت‌های UI اکنون اصلاح شده و مرز دائمی TypeScript تنظیم شده است؛ موفقیت‌های زیر مربوط به اجرای واقعی پس از اصلاح‌اند.

## نتایج واقعی بررسی
همه فرمان‌های زیر از ریشه پروژه اجرا شدند؛ exit code برای هر فرمان ۰ بود.

| فرمان دقیق | نتیجه | خطا/هشدار |
|---|---|---|
| `npm test` | موفق؛ بخش اول ۶۴/۶۴ و بخش سرور ۹۷/۹۷؛ مجموع ۱۶۱ موفق، ۰ ناموفق، ۰ ردشده | خطا نداشت |
| `npm run db:validate` | موفق؛ schema معتبر است | خطا نداشت؛ این فرمان به PostgreSQL وصل نمی‌شود |
| `npm run typecheck` | موفق؛ `prisma generate && tsc --noEmit` کامل شد | خطا نداشت؛ بررسی کامل پروژه اصلی با tsconfig اصلاح‌شده بود |
| `npm run build:app` | موفق؛ build و بررسی TypeScript کامل شد و ۹۳ صفحه تولید شد | فقط هشدار `metadataBase` برای تصویرهای Open Graph/Twitter |

تست هدفمند سرور نیز با فرمان `node --conditions=react-server --import tsx --test tests/server/contact-replies.test.ts tests/server/customer-account.test.ts tests/server/customer.test.ts tests/server/shipping-checkout.test.ts tests/server/support.test.ts` اجرا شد: ۳۷ موفق، ۰ ناموفق، ۰ ردشده.

یک اجرای محدود اولیه پیش از ترمیم `tsconfig.json` با exit code ۱ متوقف شد: چهار فایل تست به‌دلیل JSON خراب و resolve نشدن aliasهای `@/` اصلاً بارگذاری نشدند. تنظیم اصلاح شد، Prisma Client تولید شد و اجرای محدود نهاییِ بالا با موفقیت پایان یافت؛ این خطای موقت جزو نتیجهٔ `npm test` رسمی نیست.

### PostgreSQL و مرورگر
- تست PostgreSQL جدید در `tests/integration/postgres.test.ts` اضافه شده، اما اجرا نشده است؛ متغیر `ROYA_INTEGRATION_DATABASE_URL` در محیط تنظیم نیست. `DATABASE_URL` نیز خالی بود. برای حفاظت از داده‌ها تست integration به دیتابیس مجزای `roya_test` نیاز دارد و به دیتابیس واقعی متصل نشد.
- تست مرورگر اجرا نشده است؛ در این محیط مرورگر/محیط E2E آزمایشی فعال و پیکربندی‌شده‌ای برای این سناریو فراهم نبود.
- هیچ سرویس واقعی پیامک یا پرداخت فراخوانی نشد. تست‌های اجراشده از mock/stub استفاده کردند.
