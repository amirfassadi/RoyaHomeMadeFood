# اتصال دامنه به پیش‌نمایش خصوصی VPS

هدف این مرحله، دسترسی به `royahealthyfood.ir` با HTTPS و محافظ ورود خصوصی است. پرداخت، سفارش واقعی، پیامک و نمایه‌سازی همچنان خاموش می‌مانند. ورود مدیر مستقل از محافظ دسترسی آزمایشی باقی می‌ماند.

## بررسی اولیه

از سورس GitHub با commit و SHA-256 ثابت، این فرمان در ترمینال VPS اجرا می‌شود:

```bash
sudo python3 deploy/inspect-private-domain.py
```

بررسی فقط نسخهٔ نصب‌شده، وضعیت سرویس و راه‌اندازی خودکار، تطبیق پرچم‌های خصوصی، ابزارهای موجود، نام دامنه‌های Nginx، نام zoneها و viewهای BIND، پورت‌ها و منابع آزاد را گزارش می‌کند. محتویات فایل محیط، رمز ادمین، کلید نشست، کلید خصوصی TLS، کلید TSIG و تنظیمات کامل چاپ نمی‌شوند. گزارش بر پایهٔ نسخهٔ نصب‌شدهٔ `4497131e733c07627316685e3b91e7a62af75627` است و در نسخهٔ متفاوت متوقف می‌شود.

اسکریپت هیچ رکورد DNS یا پیکربندی نمی‌نویسد، سرویس را راه‌اندازی مجدد نمی‌کند و دیتابیس را تغییر نمی‌دهد. نام‌سرورها پس از تأیید میزبان DNS تعیین می‌شوند؛ نام‌سرور تازه یا آدرس ساختگی وارد ایرنیک نمی‌شود.

## ترتیب استقرار

1. انتخاب میزبان DNS بر اساس گزارش؛ اگر DNS موجود VPS مناسب بود، فقط zone جدید رویا با حفظ دامنه‌های قبلی آماده و بررسی شود.
2. آماده‌سازی ورودی مخصوص دامنه با محافظ خصوصی؛ تمام صفحات، فایل‌های برنامه و APIها محافظت شوند. مسیر عمومی صدور گواهی فقط فایل challenge را سرو کند.
3. تنظیم نام‌سرورها در ایرنیک و رکوردهای دامنه در میزبان DNS؛ تأیید پاسخ authoritative و عمومی. مقصد برنامه‌ریزی‌شده A برای ریشه به `87.107.54.244` و CNAME برای www به ریشه است.
4. صدور HTTPS، آزمون تمدید و بارگذاری با حفظ گواهی‌ها و وب‌سایت‌های قبلی.
5. ساخت و تنظیم برنامه برای مبدأ HTTPS واقعی؛ تغییر DNS به‌تنهایی URL ورود، کوکی امن و مبدأ درخواست برنامه را تغییر نمی‌دهد. نسخهٔ localhost فعلی مسیر بازگشت باقی بماند تا آزمون دامنه تمام شود.
6. آزمون رد کاربر ناشناس، ورود خصوصی، ورود/خروج مدیر، APIهای مجاز و نامجاز و مسیر مهمان شبیه‌سازی‌شده. دریافت نرخ بازار، با انتقال پول متفاوت است؛ مسیرهای عملیات واقعی باید همچنان STAGING_ONLY بمانند.

نصب اولیه و بررسی فقط‌خواندنی، تأیید پایان این مراحل نیستند. تغییرات Nginx، DNS و نشانی برنامه پس از آماده‌سازی بستهٔ جدا و قابل بازگشت انجام می‌شوند.

## مرحلهٔ اول: zone و ورودی وب بسته

پس از گزارش موفق بررسی اولیه، از بستهٔ GitHub بررسی‌شده اجرا شود:

```bash
sudo python3 deploy/prepare-private-domain.py
```

این مرحله بدون ساخت برنامه یا مهاجرت دیتابیس، zone جدید را به `/etc/named/named.conf` اضافه می‌کند. تنها فایل‌های جدید رویا و یک include در فایل اصلی نوشته می‌شوند. Nginx ابتدا برای ریشه و www روی HTTP پاسخ 404 می‌دهد؛ تنها مسیر ACME فایل challenge را سرو می‌کند. روی HTTPS دست‌دهی TLS عمداً رد می‌شود؛ هنوز گواهی یا اتصال به برنامه وجود ندارد. پس از تأیید این وضعیت، BIND بارگذاری و پاسخ‌های authoritative روی UDP و TCP بررسی می‌شوند.

نسخه، تنظیمات خصوصی، سلامت برنامه و zoneهای موجود پیش از تغییر بررسی می‌شوند. از تنظیمات نسخهٔ پشتیبان خصوصی ساخته می‌شود. شکست آزمون‌ها تنظیمات همین مرحله را بازمی‌گرداند. فرمان بازگشت چاپ‌شده، اگر فایل‌ها بعداً توسط اپراتور تغییر کرده باشند، از بازنویسی آن‌ها خودداری می‌کند. آزمون‌های تزریق خطا، این ترتیب و بازگشت را بررسی می‌کنند؛ آزمون native با Nginx واقعی روی پورت‌های موقت loopback و `named-checkzone` انجام می‌شود.

فقط پس از پیام `PRIVATE DOMAIN DNS PREPARED` نام‌سرورها و IP میزبان هرکدام در ایرنیک تنظیم شوند:

| نام‌سرور | IP میزبان / glue |
| --- | --- |
| ns1.royahealthyfood.ir | 87.107.54.244 |
| ns2.royahealthyfood.ir | 87.107.54.244 |

هر دو نام‌سرور فعلاً یک VPS دارند؛ این چیدمان افزونگی مستقل DNS ندارد. نام‌سرور دوم دامنهٔ قبلی به سرور دیگری اشاره می‌کند و میزبانی zone رویا روی آن تأیید نشده؛ بنابراین از آن استفاده نمی‌شود. رکورد AAAA اضافه نمی‌شود. سرویس recursion، zoneهای قبلی، گواهی‌ها، دیتابیس، اسرار و فایل محیط برنامه تغییر نمی‌کنند.

پس از تنظیم ایرنیک باید delegation و پاسخ عمومی جداگانه بررسی شوند. در این فاصله بازنشدن وب دامنه عمدی است؛ مرحلهٔ بعد گواهی معتبر، محافظ ورود خصوصی و مبدأ HTTPS برنامه را آماده می‌کند. این مرحله به‌تنهایی راه‌اندازی سایت روی دامنه نیست.

### بارگذاری غیرهمزمان Nginx و تشخیص شکست

اولین اجرای VPS پس از reload در آزمون ورودی وب متوقف شد؛ بازگشت تنظیمات موفق بود و برنامه تغییر نکرد. پاسخ HTTP دقیق در نسخهٔ قبلی ثبت نمی‌شد، بنابراین علت واقعی سرور هنوز قطعی نیست. reload صرفاً تغییر تنظیمات را به master اعلام می‌کند و فعال‌شدن workerهای تازه بلافاصله تضمین نمی‌شود. بررسی جدید تا ده ثانیه منتظر پاسخ هر دو نام دامنه با نشانگر اختصاصی تنظیمات تازه می‌ماند؛ 404 سایت قبلی به‌تنهایی آمادگی محسوب نمی‌شود. پاسخ نامناسب از ورودی جدید فوراً رد می‌شود و هیچ کاهش محافظتی انجام نشده است.

در صورت شکست، فقط روش درخواست، نام میزبان، مسیر ثابت آزمون و کد وضعیت چاپ می‌شوند؛ بدنه و هدرهای دیگر یا اسرار چاپ نمی‌شوند. پس از آمادگی نیز همهٔ مسیرها، ACME و رد TLS جداگانه آزموده می‌شوند و zone هنوز تا گذر همهٔ این آزمون‌ها فعال نمی‌شود. آزمون native اکنون Nginx را با سایت پیش‌فرض قدیمی شروع و سپس واقعاً reload می‌کند؛ چهار آزمون جدید، انتظار برای هر دو نام، رد 404 قدیمی، رد ورودی باز و گزارش خطای بدون بدنه را پوشش می‌دهند.

## مرحلهٔ دوم: HTTPS معتبر و محافظ ورود خصوصی

بستهٔ جداگانهٔ `deploy/enable-private-domain-tls.py` فقط بعد از آماده‌سازی موفق مرحلهٔ اول اجرا می‌شود:

```bash
sudo python3 deploy/enable-private-domain-tls.py </dev/tty
```

پیش از هر درخواست گواهی، نسخه و پرچم‌های خصوصی، سلامت برنامه، DNS authoritative محلی، ورودی بستهٔ مرحلهٔ اول، کاربر worker در Nginx و فعال‌بودن زمان‌بند موجود Certbot بررسی می‌شوند. Google و Cloudflare به‌صورت فقط‌خواندنی با DNS-over-HTTPS بررسی می‌شوند. اگر هیچ‌کدام مجموعهٔ کامل را تأیید نکنند، همان پرسش‌ها با `dig` مستقیماً از DNS عمومی Google روی 8.8.8.8 و Cloudflare روی 1.1.1.1 با TCP/53 پرسیده می‌شوند. تنظیم resolver، فایل hosts، zone و تنظیمات شبکه تغییر نمی‌کنند؛ پاسخ محلی authoritative جایگزین شاهد عمومی نمی‌شود.

دست‌کم یک resolver باید تمام NS/Aهای مورد انتظار، CNAME مربوط به www به ریشه و نبود AAAA برای ریشه/www را تأیید کند؛ پاسخ‌های ناقص از چند resolver با هم ترکیب نمی‌شوند. خطای اتصال، HTTP، NXDOMAIN، SERVFAIL و رکورد ناسازگار برای هر پرسش جدا گزارش می‌شوند؛ متن خام خطا، بدنهٔ پاسخ و اطلاعات پراکسی چاپ نمی‌شوند. اگر تأیید عمومی کامل نباشد، `DNS WAIT` با خروجی ۲ چاپ می‌شود؛ گواهی درخواست نمی‌شود، رمز پرسیده نمی‌شود و پیکربندی تغییری نمی‌کند.

برای تشخیص فقط‌خواندنی، بدون sudo یا دسترسی به اسرار/قفل استقرار:

```bash
python3 deploy/enable-private-domain-tls.py --dns-only
```

این حالت فقط DNS عمومی را بررسی می‌کند و هیچ گواهی، رمز، سرویس یا تنظیم سایتی را لمس نمی‌کند؛ موفقیت DNS به معنای آماده‌بودن HTTPS یا فروشگاه نیست. در اجرای VPS قبلی، خروجی مبهم «not ready or unavailable» هر دو سرویس و `DNS WAIT` دریافت شد؛ این خروجی علت اتصال را مشخص نمی‌کرد و هیچ تغییری ایجاد نکرد. بررسی مستقل بیرون VPS رکوردهای عمومی را درست نشان داد؛ تشخیص جدید برای تفکیک این دو وضعیت است.

گواهی اختصاصی با نام `royahealthyfood.ir` فقط برای ریشه و www با `certonly --webroot` دریافت می‌شود؛ افزونهٔ ویرایش خودکار Nginx استفاده نمی‌شود. گواهی موجود فقط با SANهای دقیق، اعتبار حداقل هفت روز و سیاست تمدید webroot و hook مورد انتظار پذیرفته می‌شود. سپس `renew --cert-name royahealthyfood.ir --dry-run --run-deploy-hooks` فقط تمدید همین گواهی و بارگذاری Nginx را آزمایش می‌کند. گواهی‌ها و تنظیمات تمدید نامرتبط هش‌برداری و حفظ می‌شوند. در صدور جدید، ایمیل ثبت نمی‌شود؛ حساب موجود Certbot و زمان‌بند آن بازنویسی نمی‌شوند.

پس از موفقیت گواهی و تمدید، رمز جداگانهٔ محافظ پیش‌نمایش دو بار و پنهان در ترمینال پرسیده می‌شود. رمز باید ۱۲ تا ۱۲۸ نویسهٔ ASCII قابل چاپ بدون فاصله داشته باشد. نام کاربری ثابت `roya-preview` است. رمز خام در فایل، آرگومان فرمان، سورس یا خروجی نوشته نمی‌شود؛ هش SHA-512 crypt از stdin به OpenSSL ساخته و فایل آن با دسترسی 0640 و گروه واقعی worker نگه‌داری می‌شود. رمز و حساب ادمین تغییر نمی‌کنند.

پس از فعال‌سازی، HTTP جز مسیر ACME همچنان 404 است. HTTPS برای تمام صفحات، فایل‌ها و APIها محافظ دارد؛ کاربر ناشناس و رمز غلط 401 می‌گیرند. فقط فایل ثابت `/_roya_private_ready.txt` با ورود خصوصی قابل دریافت است؛ هنوز proxy به فروشگاه وجود ندارد. آزمون محلی گواهی معتبر و SNI هر دو نام، رد مهمان و رمز غلط، ورود با رمز درست و بسته‌ماندن API برنامه را بررسی می‌کند. این محافظ مستقل از ورود مدیر است. برای آزمون دستی از پنجرهٔ خصوصی مرورگر استفاده شود؛ پس از آزمون همهٔ پنجره‌های خصوصی بسته شوند، زیرا مرورگر ممکن است اطلاعات HTTP Basic را در همان نشست نگه دارد.

پیکربندی قبلی و فرمان بازگشت خصوصی چاپ می‌شوند. در خطای فعال‌سازی، ورودی بستهٔ قبلی بازگردانده می‌شود؛ گواهی اختصاصی رویا برای جلوگیری از صدور تکراری باقی می‌ماند. بازگشت، تغییرات بعدی اپراتور و پشتیبان مخدوش را بازنویسی نمی‌کند. برنامه، دیتابیس، DNS و سرویس‌های برنامه تغییر نمی‌کنند. این مرحله ساخت اپلیکیشن یا تنظیم مبدأ نهایی نیست؛ اتصال فروشگاه با `NEXTAUTH_URL` و `NEXT_PUBLIC_SITE_URL` صحیح و آزمون کوکی/مبدأ در R21 جدا انجام می‌شود. پیام آماده‌سازی برای هر IP جدید همچنان به آینده موکول است.

آزمون‌ها از فایل‌ها، پورت‌های loopback، گواهی خودامضای موقت و Nginx جدا استفاده می‌کنند؛ CA عمومی، VPS، سفارش یا پرداخت واقعی در CI فراخوانی نمی‌شوند. مسیر تولید از اعتماد پیش‌فرض سیستم استفاده می‌کند و گزینه‌ای برای غیرفعال‌کردن اعتبارسنجی TLS ندارد.

## مرحلهٔ سوم: اتصال فروشگاه با مبدأ HTTPS و نشست امن

تنها پس از دریافت `PRIVATE TLS GATE READY`، از سورس ثابت GitHub و با کاربر amir اجرا شود:

```bash
bash deploy/connect-private-domain.sh </dev/tty
```

این بسته ۲۲۱ فایل برنامه را با manifest اختصاصی `private-domain-app-manifest.json` تطبیق می‌دهد. نسبت به نسخهٔ نصب‌شدهٔ 4497131e فقط package.json و lockfile برای ارتقای دقیق Next.js از 16.4.0 به 16.4.2 تغییر کرده‌اند؛ ۲۱۹ فایل دیگر ثابت‌اند. بررسی نهایی audit در اجرای اولیه مشکل بحرانی نسخهٔ قبلی را گزارش داد؛ این بسته پیش از تحویل، اصلاح وابستگی را نیز وارد کرده است. manifest قبلی برای شناسایی نسخهٔ نصب‌شده حفظ می‌شود و شناسهٔ سورس اصلاح‌شده 2e91933fed5e98ade0ca4b252546bad8e4d7c291 است.

سپس یک پوشهٔ سورس تازه ساخته و با `NEXTAUTH_URL` و `NEXT_PUBLIC_SITE_URL` برابر `https://royahealthyfood.ir`، بدون اسرار دیتابیس یا ادمین، build گرفته می‌شود. شناسهٔ خروجی از سورس اصلاح‌شده و مبدأ HTTPS مشتق می‌شود؛ نسخهٔ قبلی حفظ می‌شود. قفل استقرار حین build برقرار است و مرحلهٔ فعال‌سازی با قفل مستقل، تمام پیش‌نیازها را دوباره می‌سنجد. DNS، گواهی و سیاست تمدید تغییر نمی‌کنند.

بسته رمز موجودِ محافظ خصوصی را یک بار پنهان می‌پرسد تا ورود درست را تأیید کند؛ این رمز جدید یا رمز ادمین نیست. نسخهٔ تازه با کاربر roya-store و همان محدودیت‌های systemd، روی `127.0.0.1:3312` جدا راه‌اندازی و آزمایش می‌شود؛ برنامهٔ قبلی روی 3311 و ورودی ثابت خصوصی در این فاصله فعال می‌مانند. بعد از موفقیت کاندید، پشتیبان خصوصی محیط، سرویس و تنظیم رویا نگه‌داری و نسخهٔ اصلی روی 3311 جابه‌جا می‌شود. سپس Nginx پشت همان محافظ موجود به آن وصل می‌شود. سرویس و فایل محیط موقتِ کاندید پس از آزمون حذف می‌شوند.

برای ریشه، تمام صفحات، فایل‌های Next.js و APIها به رمز خصوصی نیاز دارند. هدر Authorization محافظ به برنامه فرستاده نمی‌شود؛ Host و X-Forwarded-Proto/Host در پروکسی به مقادیر مشخص دامنه و HTTPS محدود و هدرهای جغرافیایی و Forwarded ورودی حذف می‌شوند. www ابتدا همان رمز را می‌خواهد و پس از ورود، مسیر و query را با 308 به دامنهٔ اصلی منتقل می‌کند. HTTP همچنان جز مسیر عمومی ACME بسته است. اعلان IP جدید در این گام اجرا نمی‌شود.

آزمون نصب، صفحات FA/EN و سبد/checkout/نرخ‌ها، کاتالوگ و سیاست مشترک، APIهای بسته، URLهای canonical، کوکی CSRF با پیشوند __Host- و ویژگی‌های Secure/HttpOnly/SameSite، رد Origin نامعتبر و خروج بدون نشست در مبدأ درست را می‌سنجد؛ حساب ادمین، قیمت‌ها، محصولات و سفارش‌ها را نمی‌نویسد. CI جداگانه مسیر واقعی Nginx → Next.js → PostgreSQL آزمایشی را با ورود/نشست/خروج ادمین و کوکی __Secure-، فایل‌های مرورگر، Origin ادمین و بازگشت به محافظ ثابت نیز اجرا می‌کند. این موفقیت، جایگزین آزمون مرورگر و حساب واقعی روی دامنه در R22 نیست.

در خطای فعال‌سازی، ابتدا ورودی ثابت HTTPS رمزدار بازگردانده می‌شود، سپس محیط/سرویس/نسخهٔ برنامهٔ قبلی برمی‌گردند. بازگشت پیش از هر نوشتن، هش تمام هدف‌ها و نسخه‌های پشتیبان را بررسی و ویرایش بعدی اپراتور یا پشتیبان مخدوش را رد می‌کند. نسخهٔ ساخته‌شده و پوشهٔ سورس برای بررسی باقی می‌مانند و خودکار بازنویسی یا پاک نمی‌شوند. مسیر بازگشت زیر `/var/backups/roya/domain-origin-…/restore.sh` چاپ می‌شود؛ بازگشت این مرحله محافظ و گواهی HTTPS را حفظ می‌کند.

خروجی موفق `PRIVATE DOMAIN STOREFRONT READY: https://royahealthyfood.ir/fa/catalog/` است. ورود ادمین از `/admin/login/` با حساب قبلی انجام می‌شود. پس از این مرحله، ابزارهای قدیمی آزمون که Origin آن‌ها localhost است برای آزمون مبدأ نهایی مناسب نیستند؛ از دامنهٔ HTTPS استفاده شود. سفارش، پرداخت، پیامک، ثبت‌نام پیامکی و ایندکس موتور جست‌وجو همچنان خاموش‌اند و این نصب migration یا seed ندارد.

## بررسی پس از اتصال و ورود حساب واقعی روی HTTPS

بدون build، نصب، تغییر رمز یا محصول، از سورس ثابت GitHub اجرا شود:

```bash
sudo -v
/opt/roya/tools/node/bin/node deploy/diagnose-domain-admin.mjs --status-only </dev/tty
/opt/roya/tools/node/bin/node deploy/diagnose-domain-admin.mjs </dev/tty
```

حالت اول وضعیت active/enabled سرویس برنامه و Nginx، نحو Nginx، نسخهٔ نصب‌شده، مبدأ HTTPS، پرچم‌های خاموش، شنوندهٔ loopback، نبود کاندید موقت و حافظه/دیسک آزاد را می‌خواند؛ گواهی مورداعتماد و رد دسترسی ناشناس از Nginx محلی با Host/SNI واقعی دامنه بررسی می‌شوند. این گزارش، تأیید زمان‌بندی پشتیبان یا نگهداری لاگ و پایداری طولانی‌مدت نیست.

حالت دوم رمز موجود محافظ خصوصی، سپس موبایل و رمز ادمین را پنهان در همان ترمینال می‌پرسد. پس از خواندن وضعیت حساب و محدودیت تلاش، فقط یک ورود انجام می‌دهد؛ نشست، صفحات/API محصولات و تنظیمات، کوکی‌های امن و خروج با رد API پس از خروج بررسی می‌شوند. رمزها و کوکی‌ها چاپ یا ذخیره نمی‌شوند؛ حساب یا محدودیت تلاش بازنشانی نمی‌شود. ورود معمولی می‌تواند audit و شمارندهٔ احراز هویت موجود را تغییر دهد؛ محصول، سیاست قیمت‌گذاری، سفارش، پرداخت و پیامک نوشته نمی‌شوند.

اتصال به 127.0.0.1:443 با نام گواهی royahealthyfood.ir است؛ اعتماد TLS عادی سیستم و بررسی نام گواهی حفظ می‌شوند. ابزار، درستی زنجیرهٔ محلی Nginx تا برنامه و حساب واقعی را تأیید می‌کند و جایگزین آزمون مرورگر، دسترسی بیرونی، نمایش موبایل یا خرید مهمان نیست. خروجی موفق DOMAIN ADMIN PASS است. اگر رمز رد شود، تلاش خودکار دوباره انجام نمی‌شود. ابزار قدیمی diagnose-vps-admin.mjs همچنان فقط برای نسخهٔ localhost پیشین باقی است.

## آزمون نوشتنیِ محصول روی دامنه

پس از DOMAIN ADMIN PASS، ابتدا پشتیبان تازه و بازیابی جدا تأیید شوند؛ سپس آزمون محصول اجرا شود:

```bash
sudo -v
sudo -n python3 deploy/backup-before-admin.py
/opt/roya/tools/node/bin/node deploy/test-vps-admin.mjs --domain --catalog </dev/tty
```

ابزار رسید پشتیبان را با نسخه و هش محیط همین اجرا و عمر حداکثر دو ساعت تطبیق می‌دهد. سرویس، مبدأ HTTPS و پرچم‌های بسته نیز پیش از ورود بررسی می‌شوند. رمز محافظ و ادمین در ترمینال پنهان وارد می‌شوند. یک محصول اختصاصی با نام و اسلاگ تصادفی ساخته می‌شود؛ قیمت، موجودی، ظرفیت، صفر و نامحدود، ورودی نامعتبر، ویرایش قدیمی، فعال‌سازی و نمایش جزئیات فارسی/انگلیسی و مقادیر به‌روز ویترین آزمایش می‌شوند.

همان probe تحویلی، در CI با Nginx/NextAuth/PostgreSQL جدا اجرا می‌شود؛ مسیر localhost قبلی نیز از همین probe استفاده می‌کند. محصول در پایان آرشیو و خروج آن از کاتالوگ تأیید می‌شود. اگر آزمون میانهٔ راه متوقف شود، cleanup پیش از خروج تلاش می‌شود؛ در شکست پاک‌سازی، اسلاگ محصول برای بررسی چاپ و آزمون ناموفق اعلام می‌شود. محصولات قبلی، سیاست قیمت‌گذاری و سفارش‌ها و پرداخت‌ها تغییر نمی‌کنند. این مرحله آزمون API روی HTTPS است و جای فرم‌های مرورگر یا عکس و رسانهٔ محصول واقعی را نمی‌گیرد. خروجی نهایی DOMAIN PRODUCT PASS است.
