# گزارش تکمیل ثبت‌نام مشتری

## وضعیت

**تکمیل‌شده در کد؛ اعتبارسنجی کامل CI در این محیط محدود شد.** مسیر ثبت‌نام بدون OTP و ورود با رمز پیاده‌سازی شده و تست‌های واحد/سرور موفق‌اند. بررسی کامل TypeScript و build به دلیل خطاهای موجود در پوشهٔ ازقبل‌موجود `RoyaHomeMadeFood` کامل نشد؛ تست PostgreSQL نیز به علت نبود تنظیم اتصال پایگاه‌دادهٔ آزمایشی اجرا نشد.

## رفتار قبلی و فعلی

- **قبلی:** فرم نام، موبایل و ایمیل را هم‌زمان اجباری می‌کرد؛ API ثبت‌نام ابتدا کد پیامک می‌فرستاد و تأیید موبایل برای ساخت حساب لازم بود. ورود و بازیابی حساب نیز موبایل تأییدشده را شرط می‌کرد.
- **فعلی:** ثبت‌نام با ایمیل یا موبایل معتبر (یا هر دو) و رمز عبور ممکن است. نام، رمز حداقل ۱۲ نویسه‌ای، تکرار رمز و رضایت پیامکی اختیاری حفظ شده‌اند. ارسال/ورود کد در این مسیر انجام نمی‌شود. پس از ساخت حساب، ورود با همان شناسه و رمز انجام و کاربر به مقصد فعلی یا صفحهٔ حساب هدایت می‌شود.
- ایمیل قبل از ذخیره trim و lowercase می‌شود؛ موبایل با قواعد فعلی پروژه و تبدیل ارقام فارسی/عربی به لاتین یکسان‌سازی می‌شود. حساب تکراری با جست‌وجوی بدون حساسیت به بزرگی حروف ایمیل و قیدهای یکتای دیتابیس رد می‌شود. رمز با سازوکار فعلی scrypt ذخیره می‌شود.

## تصمیم‌های اجرایی و فرض‌ها

- مدل فعلی `User` از قبل ایمیل و موبایل nullable و unique دارد؛ هر دو تماس در ثبت‌نام جدید اختیاری‌اند، ولی حداقل یکی باید وارد شود.
- اگر هر دو شناسه داده شوند، هر دو ذخیره می‌شوند؛ هیچ‌کدام صرفاً به‌دلیل فرمت معتبر، تأییدشده محسوب نمی‌شوند.
- محدودیت نرخ ثبت‌نام به‌صورت سراسری و برای هر شناسه با bucketهای موجود اعمال می‌شود.
- مسیرهای API و منطق OTP قبلی برای استفادهٔ آینده حفظ شدند؛ فرم جدید آن‌ها را فراخوانی نمی‌کند.
- نشست ورود با Credentials/NextAuth فعلی ساخته می‌شود. بازگشت خودکار از طریق `signIn` پیاده‌سازی شده؛ اگر ورود خودکار پس از ایجاد حساب ناموفق شود، فرم به ورود با شناسهٔ ثبت‌شده تغییر می‌کند.

اجرای `next build`، فایل تولیدشدهٔ `next-env.d.ts` را به مسیرهای `.next/types` بازنویسی کرد؛ چون فایل ابتدا به مسیرهای `.next/dev/types` اشاره می‌کرد، ارجاع‌های حالت توسعه را برگرداندم. فایل همچنان modified است، مطابق وضعیت اولیه.

## OTP و وضعیت تأیید

- در ثبت‌نام جدید، `User.mobileVerifiedAt` و `User.emailVerifiedAt` هر دو صریحاً `null` ذخیره می‌شوند.
- فرم، APIهای ارسال/تأیید کد و مرحلهٔ بازیابی ثبت‌نام OTP را فراخوانی نمی‌کند؛ هیچ پیامک یا ایمیلی برای ثبت‌نام جدید ارسال نمی‌شود.
- مسیرهای OTP و جدول `CustomerRegistration` حفظ شده‌اند. در مسیر قدیمی، فقط تأیید واقعی کد همچنان می‌تواند فیلد تأیید مربوط را ثبت کند.
- قابلیت‌هایی که از قبل موبایل تأییدشده می‌خواهند (از جمله مدیریت آدرس، تغییر رمز و پشتیبانی) همچنان محدودند و در UI توضیح داده می‌شوند.

## نتیجهٔ سناریوها

نتایج زیر از تست‌های schema و سرویس با دیتابیس mock به‌دست آمده‌اند؛ اجرای مرورگر یا PostgreSQL واقعی انجام نشده است.

| سناریو | نتیجه |
|---|---|
| ثبت‌نام با ایمیل | موفق؛ ایمیل trim/lowercase شد، موبایل خالی به‌صورت `null` ذخیره شد و هر دو فیلد تأیید `null` ماندند. |
| ثبت‌نام با موبایل | موفق؛ رقم‌های فارسی به لاتین تبدیل شدند، ایمیل خالی `null` شد و هر دو فیلد تأیید `null` ماندند. |
| شناسهٔ تکراری | رد شد؛ ایمیل با تفاوت حروف بزرگ/کوچک و موبایل نرمال‌شده شناسایی شدند؛ حساب جدید و quota جدید ایجاد نشد. |
| ورودی نامعتبر | schema ایمیل نامعتبر، موبایل با طول/قالب نامعتبر، نبود هر دو شناسه و رضایت پیامکی بدون موبایل را رد کرد. |
| ورود پس از ثبت‌نام | سرویس احراز هویت با ایمیل یا موبایل تأییدنشده و بدون تنظیم OTP، شناسهٔ کاربر را برگرداند. `signIn` و انتقال مقصد در فرم پیاده‌سازی شده‌اند، اما کوکی نشست و هدایت واقعی در مرورگر E2E نشدند. |

## بررسی‌ها و تست‌ها

- `npm test` — **موفق**؛ ۶۴ تست عمومی و ۹۴ تست سرور، مجموعاً ۱۵۸ تست، بدون شکست.
- `npm run db:validate` — **موفق**؛ schema معتبر است.
- `npx tsc --noEmit -p tsconfig.signup-check.json` — **موفق**؛ بررسی scoped سورس مخزن بدون پوشهٔ محافظت‌شده. فایل موقت پس از بررسی حذف شد.
- `npm run typecheck` — **ناموفق در این worktree**؛ پس از تولید Prisma Client، خطاهای TypeScript فقط از فایل‌های `RoyaHomeMadeFood/` گزارش شد که به `src/generated/prisma/client` محلی آن پوشه ارجاع می‌دهند و فایل تولیدشده را ندارند. سورس آن پوشه تغییر داده نشد.
- `npm run build:app` — **ناقص**؛ کامپایل Next.js موفق شد، اما مرحلهٔ TypeScript به همان خطاهای `RoyaHomeMadeFood/` متوقف شد.
- `npm run deploy:check` — **ناموفق در این محیط محلی**؛ متغیرهای لازم محیط استقرار در محیط محلی حاضر نبودند. هیچ مقدار محرمانه‌ای در این گزارش درج نشده است.
- PostgreSQL integration — **اجرا نشد**؛ `ROYA_INTEGRATION_DATABASE_URL` تنظیم نشده بود، بنابراین به دیتابیسی متصل نشدم.
- `git diff --check` — **موفق**؛ خطای whitespace در diff گزارش نشد.

## متغیر محیطی و migration

- migration جدید لازم نیست؛ nullable بودن ایمیل/موبایل و فیلدهای تأیید در schema فعلی وجود دارد.
- متغیر جدیدی لازم نیست. ثبت‌نام/ورود با رمز از تنظیمات موجود دیتابیس، `CUSTOMER_ACCOUNTS_ENABLED=1` و `NEXTAUTH_SECRET` معتبر استفاده می‌کند.
- `CUSTOMER_OTP_SECRET` و تنظیمات Kavenegar برای ثبت‌نام/ورود با رمز لازم نیستند؛ مسیرهای OTP قدیمی در صورت استفاده همچنان به تنظیمات خود نیاز دارند.

## محدودیت‌ها و موارد باقی‌مانده

- تست end-to-end با PostgreSQL یا مرورگر اجرا نشد؛ رفتار واقعی cookie/session و redirect نیازمند آزمون در محیط دارای دیتابیس آزمایشی است.
- حساب تأییدنشده می‌تواند وارد شود و صفحهٔ حساب را ببیند، اما عملیات حساس وابسته به موبایل تأییدشده همچنان محدود است. پس از افزودن فرایند تأیید موبایل برای حساب‌های موجود، می‌توان این محدودیت‌ها را بازبینی کرد.
- اجرای رسمی typecheck/build در این workspace تا رفع ارجاع‌های Prisma تولیدشده در `RoyaHomeMadeFood/` کامل نمی‌شود؛ آن پوشه عمداً دست‌نخورده باقی ماند.
- مورد نیازمند تصمیم/بازبینی بعدی: اگر قرار است کاربرِ بدون موبایل تأییدشده بتواند آدرس ذخیره کند، رمز را تغییر دهد یا از پشتیبانی استفاده کند، سیاست تأیید آن قابلیت‌ها باید جداگانه تعیین شود.
